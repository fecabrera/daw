route loss when focus panic arrived before queued routing changes were consumed.

## Follow-up: transport-cache restoration omitted live voices

The user reported that live input still failed after restarting and reopening the
existing project, including after device cycling. The preceding queue/publication
checks did not cover live voice capacity after transport-cache restoration and
therefore did not establish that this report was resolved.

A read-only probe of the reported project's MIDI instruments produced sound with
direct renderer preparation. Restoring the same plans through `TransportCache`
left both instruments unable to accept live attacks. Preparing the live reserves
on the restored renderers made both instruments accept notes and produce nonzero
PCM with their effects retained. No project or source files were changed. The
scratch probe and results remain in ignored `work/` files.

The output worker created a renderer with live reserves, then replaced it with a
cache snapshot that deliberately excludes them. It now prepares live reserves
again after cache restoration and reconciles the output-state memory lease before
publication. Offline caches continue to exclude device-only live reserves.

The regression uses the actual output preparation worker and cached transport
restoration at frame zero and a nonzero saved frame. With reserve preparation
removed, the test fails because attacks cannot acquire a live voice. With the fix,
both targets accept attacks, produce audible PCM without callback heap work and
keep the stopped playhead fixed. All 97 output tests passed.
