# Documentation and dependency licenses

## Independent time-stretch implementation

- Timestretch has a mandatory independent implementation rule: under no circumstances take code directly from Rubber Band. Do not copy, translate, port, adapt, or mechanically rewrite its implementation code, tests, comments, tables, or implementation-specific pseudocode, including through AI tools or intermediary projects. Do not inspect its implementation source to guide the new engine. Use public papers, mathematical descriptions, and documented behavior, and record provenance and prior exposure honestly. Independently written adapters may call the separately licensed Rubber Band library through its public API for comparison and the existing backend; keep it outside the BSD engine's dependency graph. No licensing offer, deadline, or acceptance result waives this rule. Follow [the full rule](../../../specs/audio/timestretch.md#mandatory-independent-implementation-rule) and [independent implementation gate](../../../specs/acceptance/timestretch.md#independent-implementation-gate).

## Documentation placement and organization

- Keep README focused on the project: its purpose, current features, limitations, planned work, and documentation/license links. Keep Windows, macOS, and Linux prerequisites, build steps, packaging, plugin builds, CI downloads, and build troubleshooting in `docs/development/`, with a short link from README. Put contribution rules, architecture guidance, and validation workflows in `AGENTS.md` and its linked instruction files. Put user instructions in `docs/` and implementation requirements and acceptance criteria in `specs/`; update the appropriate files when behavior or architecture changes.
- Keep README's **Current features** section at a high level. Summarize user-facing capabilities and list all available instrument components and effects. Link to detailed documentation instead of describing individual controls, gestures, shortcuts, parameter ranges, UI dimensions/colors, or implementation rules.
- Keep README's **Status and planned work** section at a high level. Summarize the current state, important limitations, and planned capabilities. Put task-oriented interaction guidance in `docs/`. Put exact UI layout rules and internal architecture in `specs/`.
- Treat `docs/` outside `docs/development/` as user-facing documentation only. Keep practical build, setup, packaging, and CI guides for developers in `docs/development/`; contributor rules stay in `AGENTS.md` and its linked instruction files and implementation contracts stay in `specs/`. Explain how to complete tasks, use controls, interpret results, and handle practical limits or failures. Include defaults, units, and ranges when they help a user operate the application. Describe current behavior in the present tense and clearly label planned features.
- Put implementation material exclusively in `specs/`: crate/module ownership, APIs and symbols, algorithms, schemas and migrations, stable IDs, callback/threading rules, exact widget geometry or paint rules, dependency research, implementation plans, acceptance matrices, commands/results from development checks, and validation history. Keep contributor instructions in `AGENTS.md` and its linked instruction files. A parameter range or audible limitation belongs in a user guide; the code and test contract that enforces it belongs in a specification.
- For user-visible changes, update the relevant user guide and implementation specification separately. Write each for its audience; do not copy implementation paragraphs into `docs/` or append dated engineering change logs there. For internal-only changes, update only the relevant specification and validation record. User guides do not need changes merely because an internal API changed.
- Organize both trees by topic. Put effect-unit guides/specifications in `docs/effects/` and `specs/effects/`, view guides/contracts in `docs/views/` and `specs/views/`, and instrument components in each tree’s `instruments/` folder. Use `modulation/`, `editing/`, and `audio/` for those topics. Put project/save/export guides in `docs/projects/`; keep global architecture in `specs/architecture/`, acceptance plans in `specs/acceptance/`, and executed-check history in `specs/validation/`. Keep topic documents out of the tree roots; reserve roots for indexes and high-level overviews. Reuse existing topic folders before creating another category.
- When a document covers several topics, give each topic a section with a descriptive heading. Keep related instructions, explanations, and limits together. In user guides, order sections by the reader's workflow where it applies.
- When moving technical material out of a user guide, preserve requirements, decisions, provenance, and historical validation evidence in `specs/`. Update incoming links and anchors. Keep user-guide navigation in `docs/README.md` and technical navigation in `specs/README.md`. Check documentation links and review `docs/` for implementation leakage before completion.
- For behavior changes, record completed checks in `specs/validation/README.md`: behavior covered, commands/results, and remaining native/device/platform checks. Retain historical evidence and identify superseded behavior clearly. Do not claim a check that was not run.
- Document defaults, units, bounds, cancellation, and failure behavior. Keep confirmed requirements separate from proposals. Use numbered steps for procedures and tables for comparisons. Use repository-relative links and verify that targets exist.
- Keep versions tied to Cargo manifests/lockfile and the toolchain file; avoid copying changing test counts or versions into the repository instructions. Update the applicable instruction files when structure or workflow changes.

## Dependency notices

- Keep original source copyright and license notices. The repository's original code has the BSD license in `LICENSE`; bundled third-party code has its own license terms.
- When adding or changing a bundled dependency, retain its license and source notices and update packaging. Do not remove notices because a library is linked statically.
- Media notices belong in `crates/media/assets/licenses`. Preserve Rubber Band's GPL v2 text in `RubberBand-GPL.txt`, its source notice, and the Speex and KissFFT notices, including `RubberBand-Speex.txt`. Preserve LAME notices as well.
- EQ dependency notices belong in `crates/equalizer/assets/licenses`; packaging includes them with the oscillator notices.
- Oscillator dependency notices belong in `crates/oscillator/assets/licenses`; macOS packaging includes them. Keep the same notices with other distributions.
- Font assets/notices belong in `crates/unit-ui/assets`; icon assets/notices stay in `crates/ui/assets`. Other shared font notices belong in `crates/unit-ui/assets/licenses`, DAW UI dependency notices in `crates/ui/assets/licenses`, and plugin window notices in `crates/plugin-window/assets/licenses`. `tools/package_macos.sh` copies these notices into the bundle; keep equivalent notices with other distributions.
